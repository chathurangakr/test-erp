# Inventory Rules — Coconut Factory ERP

> **Status:** ✅ **IMPLEMENTED** (Phase 3), and driven by Purchasing (Phase 4), Sales
> (Phase 5) and Production — dehusking (Phase 6), husk chipping (Phase 7) and copra
> (Phase 8). Goods receipts post `PURCHASE_RECEIPT`, deliveries post `SALES_ISSUE`, and all
> three production types post `PRODUCTION_CONSUMPTION` plus `PRODUCTION_OUTPUT`. The whole
> chain is exercised together by `docs/END_TO_END_VALIDATION.md`. The husk rework added
> pooled (lot-free) stock (§15), the litre unit (§16), and two transaction types:
> `BACKFLUSH_ISSUE` (raw husk issued by a delivery) and `LOT_CONSOLIDATION` (§11).

## 1. The fundamental rule

**Stock must be derived from inventory transactions.**

On-hand quantity is *always* computed from `inventory_transaction_lines`. It is never read
from a stored total.

**Implementation:** `App\Services\Inventory\StockQueryService`.

## 2. Prohibited

**Never directly maintain inventory by simply changing a product stock field.**

- There is **no `current_stock` column on `products`** (or on `warehouses`) — enforced by
  an automated test.
- No `UPDATE products SET stock = ...` exists anywhere.
- **No unit conversion** — no NOS↔KG, KG↔L or husk↔KG/L factor on any table (§16).
- **No cache.** Every figure on every screen is computed from the ledger on request. If a
  performance cache is ever added it must be documented as non-authoritative and
  rebuildable from the ledger — none exists today.

**Why:** a stored total has no history. If it drifts, there is no way to discover when or
why. A ledger can always be recomputed and audited.

## 3. How stock is calculated

Every line stores a **positive** quantity plus a `direction` of `IN` or `OUT`. Direction
alone decides the sign.

```
quantity = SUM(IN quantity)   − SUM(OUT quantity)
value    = SUM(IN total_cost) − SUM(OUT total_cost)
```

Because every OUT line records the weighted-average unit cost **in force at the moment it
was posted**, value is a simple signed sum — no ledger replay is needed, and the remaining
value is always correct.

Stock is queryable at four grains:

| Grain | Method |
| --- | --- |
| Product (company-wide) | `quantityForProduct()` |
| Product + warehouse | `quantityForProductInWarehouse()` |
| Lot | `quantityForLot()` |
| Product + warehouse + lot | `quantityForProductWarehouseLot()` |

## 4. Required fields on every stock movement

| Field | Column | Notes |
| --- | --- | --- |
| product | `product_id` | FK, restrict on delete |
| warehouse | `warehouse_id` | FK, **required on every line** |
| quantity | `quantity` | `decimal(20,3)`, always positive |
| secondary quantity | `secondary_quantity` | `decimal(20,3)`, nullable — §7 |
| UOM | *(from the product)* | Primary/secondary UOM live on `products` |
| direction | `direction` | `IN` / `OUT` |
| transaction type | `inventory_transactions.transaction_type` | §11 |
| source record | `source_type` / `source_id` | Nullable; set by the calling document |
| date / time | `inventory_transactions.transaction_date` | |
| user | `inventory_transactions.posted_by` | FK to `users` |
| cost | `unit_cost`, `total_cost` | `decimal(20,6)` |
| lot / batch | `lot_id` | Nullable FK — §6; always NULL for new movements of pooled stock (§15) |

## 5. Negative inventory — prohibited

**Negative inventory is NOT allowed.**

Any operation that would take available stock below zero **fails atomically** — the entire
transaction is rolled back, leaving no partial movements.

**Implementation:** inside `PostInventoryTransaction`, within the same database transaction
that writes the lines:

1. Every product involved is locked `FOR UPDATE` (ordered by id, to avoid deadlocks), so
   two concurrent posts cannot both read the same pre-post balance.
2. Lines are walked **in order**, maintaining a running balance seeded from the ledger.
3. A line that would drive **product + warehouse** — or **product + warehouse + lot** —
   below zero raises a validation error, aborting everything.

The guard is checked per warehouse *and* per lot, so a lot cannot go negative even when the
warehouse holds other unlotted stock of the same product.

`TBD` — the configuration surface that would ever permit negative stock. There is none
today, and the default is "not allowed".

## 6. Lots / batches

- A lot belongs to **exactly one product**; using it for another product's movement is
  rejected.
- The lot reference on a movement is **nullable** — not every product needs lots. Whether
  a product uses lots at all is master data, `products.tracks_lots`; a pooled product
  (`false`) takes no lot anywhere — see §15.
- **Internal numbering: `LOT-YYYYMMDD-000001`**, a daily sequence generated by
  `GenerateInventoryReference`.
- The lot number **encodes no business meaning** — nothing about purchase or production.
  The origin lives in `source_type` / `source_id`, so a document can be re-classified
  without the permanent identifier becoming misleading.
- A supplier's own batch reference is stored **separately** in `supplier_lot_number`.
- Stock cannot be received **into** an inactive lot; existing lot stock can still be issued
  out.

## 7. Dual unit of measure (secondary quantity)

Raw Coconut Shell is stocked in `NOS` and also sold by `KG`.

- A movement may carry a `secondary_quantity` alongside the primary quantity.
- **No fixed conversion is ever applied.** Actual weights are entered, because shell
  weights vary.
- For a product **without** a secondary UOM, `secondary_quantity` must be `null` — supplying
  one is rejected.
- Quantities are validated against the UOM's `decimal_places` (NOS = 0, KG = 3), so a
  fractional coconut is rejected.

**Decision I-2 — secondary quantity is informational. ✅ CONFIRMED.** Because secondary quantities are
recorded only "where known", some movements legitimately carry `null` KG. The secondary
balance is therefore **not** a reliable running total and is **deliberately not guarded
against going negative**. The primary quantity is authoritative for negative-stock
prevention, and **no fixed NOS↔KG conversion exists**.

### A business process may still require a weight

"Informational" describes the **engine**, not every process that feeds it. Copra recipe
version 1 required the measured shell weight; version 2 (2026-10-18) makes it optional because
the factory has no scale for shell. The rule lives in the recipe's `requires_secondary_quantity`
flag, checked by the copra form request and posting action; the engine's behaviour is
unchanged. See `BUSINESS_RULES.md` §20.

### Value always follows the primary quantity

A product with two units is still costed in **one** of them — its primary unit. Raw shell is
valued per `NOS`:

```
allocated cost ÷ shell NOS  →  the stored inventory unit cost and the weighted average
allocated cost ÷ shell KG   →  informational only; never stored, never a weighted average
```

A screen may display the per-KG figure, clearly labelled informational. Nothing in the
costing path may read it back.

### Reversal mirrors the secondary quantity

`ReverseInventoryTransaction` copies `secondary_quantity` onto the opposite line, so a
count and its weight leave stock together and neither is left stranded. It copies the
line's authoritative `total_cost` too — see §8.1.

## 8. Costing — Weighted Average Cost

**Version 1 maintains weighted average at company/product level, not per warehouse.**
✅ **CONFIRMED** by the business.

**Incoming receipt:**

```
new average = (current value + incoming value) / (current quantity + incoming quantity)
```

**Outgoing movement:** valued at the weighted average in force at the moment of posting.
It reduces quantity and value but does **not** re-derive a purchase price. Callers may not
price an OUT line — supplying `unit_cost` on an outgoing line is rejected.

**Zero quantity is handled safely:** the average of nothing is `0`, never a division error.

### 8.1 `total_cost` is authoritative — ✅ **CONFIRMED**

A ledger line carries two money columns, and they do **not** have equal standing:

| Column | Meaning |
| --- | --- |
| `total_cost` | **The authoritative monetary value of the movement.** |
| `unit_cost` | Its **rounded per-unit representation**, normally `round(total_cost ÷ quantity, 6)`. |

**`total_cost == quantity × unit_cost` is NOT an invariant, and must never be asserted as
one.** A unit cost stored to six decimals cannot always reproduce a total that was derived
the other way round:

```
Allocated to 10C:   Rs.16,000.000000   over 280 KG
Unit cost stored:      Rs.57.142857     (the rate repeats)
280 × 57.142857   =  Rs.15,999.999960   ← NOT what the ledger stores
Ledger total_cost =  Rs.16,000.000000   ← the authoritative value
```

Before this rule, every production run quietly eroded inventory value by a few millionths of
a rupee. Individually trivial; as the opening balance of a double-entry ledger, a figure
nobody can reconcile or explain.

**What must hold instead:**

- `quantity > 0` — always, direction decides the sign;
- `total_cost >= 0` and `unit_cost >= 0`;
- `unit_cost == round(total_cost ÷ quantity, 6)` — the unit cost is an honest representation;
- therefore `|total_cost − quantity × unit_cost| <= quantity × 0.0000005` — any difference
  comes from that rounding and nothing else.

The engine enforces the last two on every line that carries a supplied total, so a caller
cannot pass a contradictory pair.

**Who may supply an authoritative total.** Only trusted domain services, through
`PendingInventoryLine::withAuthoritativeCost()`:

| Caller | Authoritative value |
| --- | --- |
| `PostGoodsReceipt` | the exact landed line value — material + allocated landed cost |
| `PostDehuskingProduction` / `PostHuskChippingProduction` / `PostCopraProduction` | the allocator's exact `allocated_cost`, unchanged |
| `TransferStock` | one figure, shared by both legs |
| `ReverseInventoryTransaction` | the original line's `total_cost`, exactly |

`PendingInventoryLine::fromArray()` — the path any request-shaped data would take — has **no
total-cost key at all**. There is no writable inventory cost field in any form, controller
or route, and a sales user still cannot price an OUT line. See `DATA_MODEL.md` **I-4**.

### 8.1a The ledger is what Finance posts

Since Finance Phase 2, a posted stock movement also writes a journal — and the amount is this
same authoritative `total_cost`, never `quantity × unit_cost`. That is what lets a general
ledger inventory control account reconcile to the inventory ledger exactly.

| Movement | Journal |
| --- | --- |
| `PURCHASE_RECEIPT` | Dr inventory / Cr Goods Received Not Invoiced |
| `SALES_ISSUE` | Dr cost of sales / Cr inventory |
| `PRODUCTION_CONSUMPTION` + `PRODUCTION_OUTPUT` | Dr output inventory / Cr input inventory |
| `TRANSFER` | **nothing** — company value is unchanged, so there is nothing to record |
| `REVERSAL` | the original journal reversed exactly |

Journals are generated only on or after the configured accounting cutover date, and the
journal is written inside the same database transaction as the stock movement. See
`ACCOUNTING_RULES.md` §13-§15.

### 8.2 Full depletion leaves nothing behind — ✅ **CONFIRMED**

An ordinary OUT movement is valued at `quantity × weighted average`. The **exception** is an
issue that takes the entire remaining company quantity: it takes the entire remaining
company **value**.

```
On hand:  13 units worth Rs.139.999999   (average rounds to Rs.10.769231)
13 × 10.769231  =  Rs.140.000003         ← would over-issue by Rs.0.000004
Issue value     =  Rs.139.999999         ← the whole remaining value

After:    quantity 0.000, value 0.000000, average 0.000000
```

**A product with no stock must be worth nothing.** Rounding would otherwise strand a residue
on an empty product, which no later process could clear — you cannot issue stock you do not
have in order to write off a fraction of a rupee.

The rule lives in one place, `StockQueryService::issueValue()`, used both by the engine
(against its in-transaction running balance) and by `TransferStock` (against the ledger
balance). The existing `FOR UPDATE` product lock makes it concurrency-safe: two issues
cannot both read the same pre-issue balance.

### 8.3 Transfers are exactly value-neutral

Both legs of a transfer receive the **same** unit cost and the **same** authoritative total,
so the OUT removes precisely what the IN puts back. The IN value is never re-derived from
the rounded unit cost. Company quantity, company value and the weighted average are all
unchanged, to the last decimal.

**All arithmetic uses BCMath via `App\Support\DecimalMath`.** PHP floating point is never
used for quantities or costs anywhere in the costing path.

**Joint-product allocation is implemented as configurable fixed percentages** held in
`production_recipe_outputs` — dehusking 85 / 15, husk chipping 30 / 30 / 40, both
provisional. One shared service, `App\Services\Production\ProductionCostAllocator`, applies
them for every production type, so the allocated output costs sum exactly to the consumed
value and production conserves inventory value: physical item count rises, money does not.
See `BUSINESS_RULES.md` §18 and §19.

**An output that produced nothing takes no value.** Only positive-quantity outputs
participate; their percentages are renormalised to 100%, and no lot is created for a grade
that measured zero. Inventory value must sit on stock that exists.

**Quantities are not always derived.** Where a recipe output's `output_ratio` is `NULL` —
every husk chipping grade — the quantity entering the ledger is the weight the **operator
measured**. There is no husk-to-KG conversion anywhere in the system, by design.

The permanent costing method — and allocation for copra — remains **`TBD`**.

## 9. Warehouse transfers

A transfer posts **one OUT from the source and one IN to the destination**, in a single
atomic transaction, with:

- the same product
- the same lot, where applicable
- **the same unit cost on both legs** — the company average at the moment of transfer

Consequently a transfer leaves company **quantity**, company **value** and the **weighted
average** all unchanged. Only the per-warehouse split moves. Tests assert all three.

Rejected: transferring to the **same** warehouse, and any transfer involving an **inactive**
warehouse. Posting to an inactive warehouse is rejected generally, not only for transfers.

**Implementation:** `App\Actions\Inventory\TransferStock`. There is no transfer UI yet.

## 10. Transaction immutability

**Posted inventory transactions and lines are immutable.**

- The models refuse `updating` and `deleting` outright by throwing, so the rule holds on
  every code path — controller, console command, tinker or a future REST API — not merely
  because no route exists.
- The **single** permitted write to a posted header is the `reversed_by_id` audit pointer,
  an append-only link to its reversal.
- The inventory module registers **read-only GET routes only**. A test asserts every
  `inventory/*` route is GET and that no `destroy` route exists.

## 11. Transaction types

`App\Enums\InventoryTransactionType` — extensible:

`OPENING_BALANCE`, `PURCHASE_RECEIPT`, `SALES_ISSUE`, `PRODUCTION_CONSUMPTION`,
`PRODUCTION_OUTPUT`, `TRANSFER`, `ADJUSTMENT_IN`, `ADJUSTMENT_OUT`, `REVERSAL`,
`BACKFLUSH_ISSUE`, `LOT_CONSOLIDATION`.

| Type | Written by |
| --- | --- |
| `BACKFLUSH_ISSUE` | `PostDelivery`, when a line's product defers its raw material to delivery (husk chipping outputs). Raw husk OUT, at the weighted average, source = the delivery. See `BUSINESS_RULES.md` §19 |
| `LOT_CONSOLIDATION` | `ConsolidatePooledLots` — the one-time move of a pooled product's old lot balances into its lot-free stock (§15). Value-neutral |

Neither of the two brings new stock (`bringsNewStock()` is false), so neither is refused for
an inactive product.

The engine supports these types; the business documents behind them are separate, later
modules.

Transaction references follow **`INV-YYYYMMDD-000001`**, a daily sequence. Like lot numbers,
the reference encodes no business meaning.

## 12. Reversal

A reversal is a **new transaction**, never an edit.

- Every original line is mirrored with the **opposite direction**.
- The reversal reuses the original line's unit cost **and its authoritative `total_cost`**,
  so it removes exactly the value that was added — never a re-derivation of it (§8.1).
- `reversal_of_id` points at the original; the original's `reversed_by_id` points back.
- **A transaction can be reversed at most once** — enforced in the action under a row lock
  *and* by a unique index on `reversal_of_id`.
- **A reversal cannot itself be reversed.**
- **A reversal that would cause negative stock is rejected**, using the ordinary guard. If
  stock has already been issued onward, the receipt that brought it in cannot be reversed.
- The original transaction and its lines are **never modified or deleted**.

**Decision I-1 — a reversal reuses the original line's unit cost**, rather than the current
weighted average. ✅ **CONFIRMED** by the business.

A reversal is an undo of one specific posting. If a receipt of 100 @ 10 were reversed after
the average had moved to 12, costing the reversal at 12 would remove 1,200 of value when
only 1,000 ever went in — silently corrupting the valuation. Reusing the original cost makes
the reversal cancel the original *exactly*, in both quantity and value.

This is a deliberate exception to the general "OUT uses current average" rule in §8, and is
now a permanent rule.

## 13. Posting is the only way in

Inventory is written **only** through `App\Actions\Inventory\PostInventoryTransaction`.
Controllers never perform inventory arithmetic. Every future module — purchasing, sales,
production — must post through this action so the guarantees above apply uniformly.

The posting sequence:

1. Validate products, warehouses (active), quantities and UOM precision.
2. Validate secondary quantity against the product's secondary UOM.
3. Validate lot ownership and lot status.
4. Open a database transaction.
5. Lock the product rows `FOR UPDATE`.
6. Compute current stock and value from the ledger.
7. Reject any OUT that would create negative stock.
8. Determine weighted-average cost for outgoing lines.
9. Create the header.
10. Create the lines.
11. Commit — all lines or none.

## 14. Inactive products — ✅ **CONFIRMED**

**An inactive product may be issued OUT, but must never receive NEW stock.**

Deactivating a product means "stop buying and making this", not "freeze whatever is left in
the warehouse". Remaining stock must still be sellable and clearable, so:

| Movement | Inactive product |
| --- | --- |
| `PURCHASE_RECEIPT` (IN) | ❌ **Rejected** |
| `PRODUCTION_OUTPUT` (IN) | ❌ **Rejected** |
| `OPENING_BALANCE` (IN) | ❌ **Rejected** |
| `ADJUSTMENT_IN` (IN) | ❌ **Rejected** |
| `SALES_ISSUE`, `PRODUCTION_CONSUMPTION`, `ADJUSTMENT_OUT` (OUT) | ✅ Allowed |
| `TRANSFER` (either direction) | ✅ Allowed |
| `REVERSAL` (either direction) | ✅ Allowed |

**Why transfers and reversals are exempt:** neither introduces new stock. A transfer
relocates stock that already exists — blocking it would strand a discontinued product in one
warehouse. A reversal undoes a posting that already happened — blocking it would make an
error uncorrectable, which contradicts §12.

**Implementation:** `InventoryTransactionType::bringsNewStock()` marks the four types that
introduce stock; `PostInventoryTransaction` rejects an IN line for an inactive product only
for those types. Goods receipt posting checks this too, to give a clearer message before
doing lot work that would be rolled back. Tests cover both the allowed and rejected paths.

## 15. Pooled (lot-free) stock — ✅ **CONFIRMED**

**A product with `products.tracks_lots = false` is ONE pooled stock.** Its movements carry
no lot, and no screen, request or kiosk step asks for one.

| Product | Lots? |
| --- | --- |
| `COCONUT`, `DEHUSKED-COCONUT`, `RAW-HUSK` | **Pooled** |
| `HUSK-7C`, `HUSK-9C`, `HUSK-10C`, `COCOPEAT` and their litre items (`-L`) | **Pooled** |
| `COPRA`, `RAW-SHELL` | Lots, as before |
| Any product created later, and the QA test product | Lots (the default) |

Which products are pooled is master data, set by `ProductSeeder` — never a product code in
application logic.

**Rules:**

- New movements of pooled stock carry `lot_id = NULL`. Traceability is to the document:
  every ledger transaction records its `source_type` / `source_id`.
- **The engine refuses stock coming IN to a lot of a pooled product**
  (`PostInventoryTransaction`), except for `REVERSAL` — which puts stock back exactly where
  it came from — and `LOT_CONSOLIDATION`.
- An OUT without a lot is guarded by the **product + warehouse** total (§5), so the pool
  can never go negative.
- A goods receipt of a pooled product **creates no lot**. A supplier's lot number typed on
  the line stays on the receipt line as information.
- Deliveries and production **refuse** a lot chosen for pooled stock, rather than silently
  ignoring it. Production creates output lots only for lot-tracked outputs: copra consumes
  pooled dehusked coconut and still gives its copra and shell new lots.
- A delivery issues pooled stock from the warehouse even while some of it still sits in an
  old lot.

**Old lots are never edited or deleted.** Stock a product held in lots before it was pooled
keeps its full history. A **one-time, recorded** move brings those balances into the pool:

```
php artisan inventory:consolidate-pooled-lots --user=owner@example.com [--dry-run] [--force]
```

It shows the plan, asks before writing, and posts ONE `LOT_CONSOLIDATION` transaction under
the named user: each lot balance leaves its lot and enters the pool in the same warehouse,
both legs at one unit cost and one authoritative total (`ConsolidatePooledLots`). Quantity,
value and the weighted average do not move, and **no journal** is written — same product,
same account. Re-running finds nothing to move.

## 16. Units — NOS, KG and L — ✅ **CONFIRMED**

Three units of measure exist: `NOS` (counted items), `KG` (weight) and `L` (litre, volume,
3 decimals — added for husk products measured by volume). "Qty" is UI wording for a `NOS`
count, not a unit.

**No conversion exists between any two units**, and none may be added — not NOS↔KG, not
KG↔L, not husks↔KG, not husks↔litres.

**A product measured both by weight and by volume is two stock items**, one per unit:

| Stock item | Unit |
| --- | --- |
| `HUSK-7C` | KG |
| `HUSK-7C-L` | L |

So 50 KG of 7C and 100 L of 7C are two balances, with two weighted averages, that never
merge or net off. The screens show them as "7C — KG" and "7C — L".

**Why not a unit column in the ledger?** The ledger holds each product's quantity in that
product's primary unit, and the weighted average is per product. Keying stock by
(product, unit) instead would change every balance query, the costing engine, transfers,
reversals and every report — and a KG/L average for one product has no meaning anyway.
Separate stock items get the same result with the engine unchanged. The two items of a
grade share their accounting mapping.
